## 中速失败已定位到 QP 可行性

第 213 个控制步首次失败，位置约为 `(5.934,-0.004,0.994)` m。
实际速度约为 `(3.570,-0.011,0.015)` m/s。

同一个保存的 QP 得到 3 项一致证据：

1. 当前 OSQP 返回 `primal infeasible`。
2. 原版 Docker OSQP-Eigen 同样返回不可行。
3. 独立 HiGHS 线性可行性检查也判定不可行。

保持走廊、位置和加速度不变，只把初始速度置零后，QP 恢复可行。
这一改动对应原版 `perfect_simu` 的状态处理。
该实验说明：当前中速失败不能靠替换 QP 求解器解决。

证据：

- `results/native-medium-diagnostic-02/first-failed-qp-0.npz`
- `results/medium-failure-oracle/diagnosis.json`
- `results/medium-failure-oracle/zero-velocity-ablation.json`

该实验只复核了同一 QP 的可行性，未完成原版完整规划器的同输入对照。
用户随后已授权真实配置使用制动重规划。
新结果单独保存，见执行配置文档。

## GPU 批量 QP 有加速，完整控制链尚未达标

测试机为共享 RTX 4090，测试时还有其他 GPU 工作负载。
下表统计 QP 组装后的求解时间，包含批量准备和传输。
CPU 和 GPU 均使用名义容差 `eps_abs=eps_rel=1e-3`。
默认数值解不保证逐位一致。

| QP 批量 | CPU 批处理耗时中位数 | GPU 批处理耗时中位数 |
| ---: | ---: | ---: |
| 1 | 2.74 ms | 37.67 ms |
| 8 | 18.02 ms | 40.56 ms |
| 64 | 138.59 ms | 61.65 ms |

64 个 QP 的求解批处理加速约为 2.25 倍。
单环境 GPU 路径反而更慢，因此默认仍保留 CPU 数值基线。
这些数字不代表空闲 GPU 的独占性能。

A*、EMVP、地图聚合和 QP 组装尚未迁移至 GPU。
10 环境端到端平均耗时约为 126–173 ms/步。
当前不能声称满足 100 Hz 墙钟实时控制。
100 Hz 在场景测试中指仿真控制频率。

性能证据为 `results/qp-benchmark/benchmark.json`。
完整步骤耗时保留在各场景的 `stage-times-ms.npy`。
